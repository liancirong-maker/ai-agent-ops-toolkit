# 案例：从零散失败到系统问题

## 背景

每天都有服务商反馈「客户分配失败」。单看每一条，都像是个别客户的问题：余额不够、已经有服务商了，或者系统报错。

## 做法

1. **先查单条**：用分配结果查询 Skill 逐个查失败原因，并记录下来
2. **发现重复**：同一个报错半个月内出现了 4 次，判断不像偶发问题
3. **全表扫描**：把分配表的全部记录拉下来，按备注内容归类
4. **推翻假设**：一开始以为是某一家服务商独有的问题，后来在另一家服务商身上也出现了同样的报错，于是把问题升级为**系统层面的登记缺陷**
5. **修正口径**：只看失败记录会高估某家服务商的问题；拉全量数据后发现成功的单子其实不少，真正的问题是大量积压、没有处理

## 结论

| 类型 | 规模 | 根因 | 建议 |
|---|---|---|---|
| 余额类 | 30+ 条，7 家服务商，持续近两个月 | 申请表写的余额门槛与系统实际门槛不一致 | 统一门槛口径，或在申请表上提示真实门槛 |
| 系统错误类 | 2 家服务商 | 服务商 ID 在两套系统中不一致：CRM 能拦截，分配系统却找不到这家服务商 → 客户流失 | 补登服务商 ID |
| 归属类 | 若干 | 提报前没核查客户归属和余额 | 提报前先查挂接 |

## 产出

- 证据文档（含时间线、样例和统计），已上报相关负责人
- 把「提报前先查挂接」写进服务商提报流程
- 把失败类型的三分法写进分配结果查询 Skill，以后查询时会自动归类

## 反思

- 同一个现象出现 3 次以上时，就应该去做全量统计，而不是继续一条条解释
- 结论要随证据更新：发现新的反例，就要推翻之前的判断
